# Technical interview questions and answers

Short answers you should be able to give (and expand on) about this project.

**1. Walk me through what happens when a user asks a question.**
The question is checked for follow-up cues and, if needed, merged with the previous question. It is embedded with `all-MiniLM-L6-v2` and searched against a FAISS inner-product index of normalised chunk vectors (cosine similarity). An evidence gate checks that the best score is above 0.30 and that the passages share an informative keyword with the question (or the score is above 0.50). If the gate fails, the app says no relevant evidence was found and shows the nearest passages. Otherwise the generator (extractive by default, or an LLM) produces an answer from the retrieved chunks, a grounding check verifies each answer sentence against the chunks, and citations with page numbers and highlighted excerpts are rendered.

**2. Why chunk documents at all, and why ~800 characters with overlap?**
Embedding models have short input limits (MiniLM truncates at 256 word pieces) and represent a passage as a single vector, so long inputs blur multiple topics together. Smaller chunks give sharper vectors and more precise citations. Overlap (150 chars) ensures a sentence or fact that straddles a boundary appears intact in at least one chunk. Chunks are sentence-aligned so they do not start or end mid-sentence, and they never cross a page so each chunk has exactly one page citation.

**3. Why FAISS `IndexFlatIP` rather than an approximate index?**
Flat search is exact and has zero recall loss; at session scale (hundreds to low thousands of chunks) a brute-force dot product over 384-d vectors takes microseconds. Approximate indexes (HNSW, IVF) trade a little recall for speed and only pay off at millions of vectors. Because vectors are L2-normalised, inner product equals cosine similarity, so scores are comparable across queries and usable for thresholds.

**4. How do you prevent the assistant from answering with unsupported information?**
Three layers: (1) the evidence gate refuses to answer when retrieval is weak; (2) the LLM prompt only contains the retrieved passages and instructs the model to answer solely from them and cite inline; (3) a post-hoc grounding check compares every answer sentence with the retrieved text and flags unsupported ones in the UI. The default extractive mode cannot hallucinate at all because it returns source sentences verbatim.

**5. How did you evaluate the system and what were the results?**
`evaluation/evaluate.py` runs 30 answerable questions with known (document, page) answers, 8 unanswerable questions and 4 two-turn follow-up conversations over the two sample PDFs. It reports Recall@1/3/5 and MRR for retrieval, keyword hit rate for answer correctness, a grounding score, abstention accuracy and follow-up recall with vs. without history. In extractive mode the measured results were Recall@1 86.7 %, Recall@3 96.7 %, Recall@5 100 %, MRR 0.918, keyword hit 100 %, all answers fully grounded, 7/8 unanswerable questions correctly declined, and follow-up Recall@3 of 100 % with history vs. 75 % without. The numbers are stored in `evaluation/results/` and regenerated by rerunning the script.

**6. What is a weakness of using cosine similarity as a relevance threshold?**
Small embedding models score *topical* similarity. "What is the library's pet policy?" scores 0.38 against the library policy even though pets are never mentioned. A fixed threshold either blocks paraphrased questions or admits such false positives. I added a lexical check that ignores corpus-frequent words, which fixed the in-domain false positives without reducing recall on the answerable set. A cross-encoder re-ranker would be the next step.

**7. How are follow-up questions handled without an LLM?**
A heuristic detects follow-ups (pronouns such as "it/they/that" or very short questions) and prepends the previous user question to the retrieval query, so the vector search still has the topic. In the evaluation this raised follow-up Recall@3 from 75 % to 100 %. In LLM modes the last few turns are also included in the prompt so the model can resolve the reference when writing the answer.

**8. Why offer an extractive mode instead of requiring an LLM?**
It keeps the project free, private and deployable on Streamlit Community Cloud with no secrets. It also acts as a safety net: if the Ollama or hosted call fails, the pipeline falls back to the extractive answer and tells the user, so the app never shows an empty response.

**9. How would you scale this to thousands of documents or many users?**
Move ingestion to a background worker, persist the index (the store already has save/load) in a managed vector database or a sharded FAISS index (IVF/HNSW), store chunk metadata in a database, cache query embeddings, and add a re-ranker. For many users, isolate indexes per tenant and run the embedding model as a separate service so the web tier stays stateless.

**10. How do you handle scanned PDFs, encrypted PDFs and non-PDF uploads?**
The loader validates the `%PDF` header, catches PyMuPDF open errors, checks `needs_pass`, and counts pages whose text is below a minimum length but which contain images. Each case yields a specific status and user-facing message (run OCR, remove the password, only PDFs are supported). Partially scanned documents are indexed with a warning about the skipped pages.

**11. What does the grounding score measure and what are its limits?**
For each answer sentence it computes the fraction of content words (and word bigrams) that appear in the retrieved passages; a sentence is "supported" above 60 % unigram or 50 % bigram coverage. It is deterministic and free, so it can run on every answer and in CI. Its limit is that it checks lexical overlap, not logic: a sentence that recombines source words into a false claim can pass. An LLM-as-judge or NLI model would catch more at a cost.

**12. Why Sentence Transformers over an API embedding model?**
Free, local, no data leaves the machine, and deterministic for tests. MiniLM is ~90 MB and embeds hundreds of sentences per second on CPU. The trade-off is lower quality than larger models; swapping to `bge-small-en-v1.5` or an API model is a configuration change because the embedder is behind a small interface.

**13. How does Streamlit's execution model affect the design?**
Streamlit reruns the script on every interaction, so expensive objects must be cached: the embedding model lives in `st.cache_resource` (shared across sessions), while the per-user pipeline, chat history and upload fingerprints live in `st.session_state`. Upload fingerprints (name + size + MD5) stop the same file being re-embedded on every rerun.

**14. What would you add next?**
A cross-encoder re-ranker, hybrid BM25 + vector retrieval, OCR integration for scanned PDFs, streaming LLM responses, persistent per-user indexes, and an LLM-based evaluation of answer quality alongside the lexical metrics.
